智慧备忘录

有备忘 · life-memory-mvp
个人项目 · 产品负责人
STORY OPENING

家里的那颗驱虫药，我明明记得还剩一粒，却怎么也找不到。重新买完，才在零食架最底层发现它——这时猫已经长大，原来的剂量也不再适用。

类似的“小事”一直发生：猫砂盆上次是什么时候彻底清洗的？想讲给妈妈的趣事，为什么总等到细节褪色才想起来？每次我都在“这个要记一下”和“算了，应该记得住”之间放弃记录。

一件物品放在哪里一件事上次何时做一段经历以后想讲
我缺的不是更复杂的知识库，而是一个能接住生活碎片、在未来需要时把它送回来的“外置记忆”。
最初构想

像发微信一样说一句，AI 自动拆成原子记录、放进固定生活模块；有日期的进入日程，之后按模块浏览或直接提问。第一版很快证明：技术能实现，但“先替所有人设计一套生活分类法”这个产品假设错了。

01

用户与场景

现阶段证据来自长期生活场景记录、竞品任务链拆解和多轮产品假设，而非已经完成的大样本调研。以下是有场景支撑、仍待真实用户验证的共性判断。

低准备输入

记录前不用先想标题、分类，或判断 AI 能否理解。

可靠留存

模型失败也不能丢原话；先保存，再理解。

多路找回

既能按人、宠物、物品浏览，也能按语义和日期搜索。

随时纠错

看得见系统做了什么，也能编辑、撤销、删除和导出。

共性背后的个性有人围绕家人整理，有人围绕宠物、住所或物品；对自动归类、日期误差、提醒和隐私的容忍度也不同。用户画像因此从“某类人”改为“频繁产生生活碎片，却不愿维护复杂结构的一类行为”。
02

第一版 Demo

第一版叫“拾光备忘”：用微信小程序 + Java / Spring Boot 手搓出可运行 Demo，先证明从一句自然语言到结构化备忘的链路能够跑通。

做到了
  • 自然语言快速记录与原文回执
  • AI 原子化、固定模块与稳定标签
  • 日历、清单、看板与搜索视图
  • Mock AI / H2 跑通完整演示
暴露的问题
  • 用户要先学懂模块、分类、标签和多种视图
  • 固定模块限制每个人不同的生活组织方式
  • 功能很多，却没有收敛到一个清晰的 MVP 假设
  • 能演示不等于能上线：持久化、异步任务和真机验收都未闭环
产品决策
  • 没有继续给第一版堆功能，而是回到用户完成“记住—找回”的最短任务链，重建信息架构。
  • 把“AI 是否能分类”降为次要问题，先保证用户的原话不会丢、系统行为可理解且可修正。
03

竞品坐标

我没有只比功能清单，而是沿着“记录 → 整理 → 找回 / 提醒”拆解每类工具在哪一步把成本留给了用户。

手机备忘录
稳定、成熟

但记录时仍要决定放在哪里，并持续维护结构。

微信自聊
入口最轻

但信息按时间沉底，后续管理与导出能力弱。

Notion / PKM
结构最强

但搭建与维护成本高，不适合“顺手记一下”。

日历 / 提醒
确定时间最强

但承接不了多数没有明确日期的生活信息。

AI 记忆产品
自动化更高

但黑盒归类、纠错、删除与导出常不够透明。

产品空位输入像聊天一样轻，查看像备忘录一样清楚；系统负责整理，用户保留最终控制权。
04

固定生活模块

系统替用户定义生活。

推翻：不符合个人心智

推翻：结构仍由系统主导
V3.1

保留：同一内容只存一次
V3.2
可靠、可纠错、可验证

AI 只给候选，程序校验，用户拍板。

06

正式开发

进入正式开发后，最难的不是“接上大模型”，而是把慢、会失败、会误判的智能能力放进一条用户仍然敢信任的链路。

问题 01
模型慢或失败，不能让记录消失

决定：本机 Outbox 暂存，服务端幂等保存 Source 后立即返回“已保存”，AI 通过事务任务异步处理。

问题 02
自动整理越强，误操作成本越高

决定：模型只生成候选；程序校验格式、日期与权限后写入，用户可以编辑、撤销和删除。

问题 03
模糊时间被猜错，比不提醒更糟

决定：“过几天”“下次”只保留原文，不强行进入“今天”；确定日期才生成日程。

问题 04
密码不是普通文本打码就够了

决定：敏感内容在正常 Source 与模型链路之前拦截，进入独立 Secure Vault 与加密边界。

已完成

V3.2 产品与交互基线、正式 HTML 原型、Java 21 / Spring Boot 模块化底座、PostgreSQL / RLS、Source-first、幂等、事务 Outbox 与统一验证。

开发中

真实微信登录、分类 / 备忘 / 记录、正式页面与编辑器、安全区、AI 候选、搜索问答、“今天”、导入导出和完整端到端验收。

atap-changelog-updater
腾讯 · 产品策划

任务背景

将产品与技术信息合并为面向用户的周度平台更新日志，并安全写入 iWiki。

原流程与成本

产品信息在周例会、技术信息在发布计划，人工拼合容易漏周、写错周；修改时还可能覆盖历史条目。

AI 实现方案

以周例会上线能力为主、TAPD 缺陷为辅，校验周期后生成用户语言，经确认再执行新增或定点修改。

{{ partial "skill-diagram.html" (dict "type" "changelog" "label" "更新日志自动生成完整流程图") }}
关键设计决策
  • 双源周期不一致立即暂停，避免把不同周的信息拼在一起。
  • 写入前必须人工确认；先读旧页面，再决定新增或修改。
  • 新增只追加并按日期排序，修改只替换目标周，防止覆盖历史。

达成效果

把双源拼合、用户化表达和 iWiki 写入收敛为可校验流程，降低错周、漏项及误覆盖风险，形成可持续维护的更新日志。

产品落地经验分享 → iWiki 案例

atap-share-to-iwiki
腾讯 · 产品策划

任务背景

把产品落地经验分享转化为其他项目组可直接复用的结构化案例。

原流程与成本

展示文档与会议录制“讲过即消失”；人工整理结构不一，智能纪要又常缺少踩坑、真实数据和问答边界。

AI 实现方案

脚本拉取逐字稿，LLM 交叉理解逐字稿与展示材料，识别口径差异并按模板成文，经用户确认后新建 iWiki 页面。

{{ partial "skill-diagram.html" (dict "type" "sharing" "label" "产品落地经验分享转 iWiki 案例完整流程图") }}
关键设计决策
  • 逐字稿是一手事实，展示材料提供结构；数字冲突以展示材料口径为准并标注。
  • 通过主题、日期、正文三点核对录制，匹配不上就停止，不用相似内容凑数。
  • 敏感信息中性化；每期新建页面不覆盖历史，写后检查章节、表格和父页面。

达成效果

将一次性分享转化为结构统一、口径可追溯的案例资产，并保留现场问答与可照搬清单，让经验从“听过”变为“可复用”。

新功能用户手册

atap-release-poster
腾讯 · 产品策划

任务背景

把研发向发布计划翻译成最终用户“一看就懂、照着能用”的图文新功能手册。

原流程与成本

原发版内容只列需求与缺陷，用户需要自行理解价值、入口和步骤；产品需人工筛选功能、确认路径、整理截图并重复排版。

AI 实现方案

从发布计划中筛出用户可感知能力，按模块生成“价值、入口、步骤、配图”四件套，经截图与入口确认后输出统一 HTML。

{{ partial "skill-diagram.html" (dict "type" "manual" "label" "新功能用户手册生成完整流程图") }}
关键设计决策
  • 只有存在页面、入口、按钮或可见结果的功能才进入手册。
  • 操作步骤严格来自需求 description 原文；缺失时留空并提示补充，不自行编造。
  • 生成前回显保留项、剔除项、入口路径和截图归属，图片使用相对路径并支持灯箱。

达成效果

12 期累计负责发版内容
200+ 成员部门覆盖
定性反馈图文步骤更易阅读

统一了用户价值、功能入口和操作步骤的传播结构。12 期是发版清单与图文手册的总期数，不能表述为全部由该 Skill 自动生成。

技术社区 sourcing 运营

tech-community-sourcing
字节跳动 · HRBP

任务背景

面向技术岗位，在 GitHub 等技术社区中寻找方向匹配的优质候选人，并把分散的公开信息整理成 HR 可直接判断和触达的候选人线索。

原流程与成本

HR 需要先学习不同社区的运营模式、主流人群、内容分享与招聘方式，再跨平台搜索、筛选和整理候选人信息；平台规则与技术语境不同，人工学习和重复检索成本高。

AI 实现方案

先沉淀技术社区画像与 sourcing 方法，再将搜索、公开证据提取、方向匹配和候选人卡片整理封装为 Skill；接入 Aime 后，可在对话中输入岗位方向并直接获得候选人结果。

{{ partial "skill-diagram.html" (dict "type" "sourcing" "label" "技术社区 sourcing 运营完整流程图") }}
关键设计决策
  • 先理解社区运营模式、主流人群和招聘路径，再确定搜索来源，避免脱离社区语境进行无差别检索。
  • Skill 负责跨社区搜索、公开信息整理和方向匹配，输出保留候选人技术活动证据，不只给出结论。
  • Aime 对话作为低门槛调用入口，结果统一为候选人卡片；最终是否触达仍由 HR 确认。

达成效果

多社区统一搜索入口
自动化筛选与信息整理
对话内候选人卡片推送

把社区学习、候选人搜索与信息梳理收敛到一个可复用入口，降低复杂人工筛选和重复学习技术社区运营方式的成本。

反馈收集流程重构

feedback-governance-workflow
腾讯 · 产品策划

任务背景

将每日新增的用户需求与缺陷完整沉淀到 TAPD 外部需求反馈池，并与已有事项或已上线能力建立关联，让反馈可统计、可排期、可闭环、可回访。

原流程与成本

反馈分散在共享表格、访谈材料和旧 Bot/TAPD，存在漏录、重复建单、字段与原始材料缺失；旧 Bot 直接理解非结构化对话建单，还会引入幻觉和字段不稳定，人工拆解、查重、补字段与搬图成本高。

AI 实现方案

以智能表单和多维表格保存原始事实，每日两次触发自动化入池 Skill；脚本、LLM 与 TAPD MCP 分别承担解析、判重和写入，人工只把关疑似重复与异常。

{{ partial "skill-diagram.html" (dict "type" "feedback" "label" "反馈收集流程重构完整流程图") }}
关键设计决策
  • 原始反馈先确定性落库，AI 不决定事实是否被保存；即使处理失败，记录仍可重试或人工补偿。
  • 已有记录只追加证据、不覆盖正文；“已实现”必须有发布或知识来源佐证，否则降级为新反馈。
  • 建单前再次检索，写入后回读真实字段；图片失败回退附件，任何不确定项交由人工确认。

达成效果

每日 2 次定时任务处理
约 2 个月持续运行
90+ 条原始反馈全部进入处理结果

平台数据运营看板

platform-ops-dashboard
腾讯 · 产品策划

任务背景

每周稳定回答平台趋势、失败归因、使用情况和成本四类问题，为 20+ 人产研测团队及管理层周会提供可比较、可行动的数据依据。

原流程与成本

初始只有粗略模板，指标、口径和取数方式未定义；整版交给 AI 一次生成会出现 SQL 报错或超时、口径漂移、长上下文幻觉与反复校对，完整产出约需 1.5 天。受合规限制，AI 也不能直连数据库。

AI 实现方案

将整版任务拆成四个独立模块，以模板、标准取数手册和模块 Prompt 锁定口径；人工执行 SQL，AI 基于真实回传数据出图与初步归因，再经人工核验和修改 SOP 合并发布。

{{ partial "skill-diagram.html" (dict "type" "dashboard" "label" "平台数据运营看板完整流程图") }}
关键设计决策
  • 看板结构高频局部变化，刻意保持半自动；稳定规则封装为节点 Skill，变化内容留在手册、Prompt 与人工控制点。
  • SQL 必须由人工执行，AI 只依据回传的真实结果出图和归因；四个模块独立运行，避免长上下文污染。
  • 范围、口径、前后周变化与异常值必须人工复核；指标变化只修改对应模块，并经过单独 SQL 测试与版本更新。

达成效果

8 周持续运营
约 1 小时单次出数，由约 1.5 天缩短
20+ 人团队与管理层周会使用

其中人工执行与核验约 30 分钟。模块化链路减少了 SQL 报错、口径漂移和重复校对，并支持从企微使用下降等异常中形成宣导动作、持续跟踪数据回升。

BOSS 直聘 HR 助手

boss-hr-screening-workflow
字节跳动 · HRBP

任务背景

将 BOSS 直聘上的候选人初筛、资格判断、标准回复和求简历串成可长期运行的自动化链路，让 HR 把精力集中在需要人工判断和深度沟通的候选人上。

原流程与成本

HR 需要逐条阅读候选人资料、对照岗位条件并重复回复。BOSS 没有 MCP，前端还通过图片化、图层隐藏文字等方式防抓取，AI 视觉读取和自动点击都不稳定，容易抓错内容或点错按钮。

AI 实现方案

用标准化脚本监听并筛选前端网络数据，把候选人必要字段传入 Coze 工作流；大模型只负责按岗位标准判断，结构化结果回传脚本后，再由脚本在 BOSS 执行回复、求简历或停止推进。

{{ partial "skill-diagram.html" (dict "type" "boss" "label" "BOSS 直聘 HR 助手完整流程图") }}
关键设计决策
  • 产品不是 Agent，也不是 MCP Tool；BOSS 无 MCP，整条链路由确定性脚本与 Coze 工作流共同完成。
  • 候选人信息通过前端抓包提取，按钮操作由脚本固定执行；不让 AI 视觉模型承担不稳定的页面抓取和点击。
  • 大模型只做语义筛选并返回受约束的结构化结果；Prompt 围绕格式、限制内容与 badcase 迭代 10+ 版后固化。

达成效果

抓包 + 脚本固定采集与页面动作
10+ 版Prompt 与 badcase 迭代
长期稳定自动筛选、回复与求简历

将不可靠的页面识别转为可重复的抓包与脚本动作，并把语义判断收敛到 Coze 工作流，最终形成可长期跑通的自动化筛选助手。
