1 Demo先行：基于「浏览器扩展」把想法做成可运行 Demo

1.1 Demo 的目标

最初的高频场景发生在网页和 Agent 界面中，因此 Chrome 浏览器扩展是验证构想最快的载体。

Demo的核心是解决“长文段选择困难”和“剪贴板互斥”两大痛点，实际跑通三件事：

  1. 点击一个字符作为一端，再点击另一个字符作为另一端；
  2. 把两端之间的网页内容保存成一个片段；
  3. 多个片段可以在悬浮面板中组合复制。

1.2 浏览器 Demo 的核心产品结构

Demo证明了：复制不一定必须是“拖过全部文字”，系统只要能够准确理解两个端点，就可以替用户完成中间范围的提取。

1.3 Demo暴露出的边界

Demo 验证了产品核心链路，但也明确限制了产品使用范围：

  • 只能处理当前标签页的标准网页 DOM；
  • 不能覆盖其他桌面软件、跨标签页或跨应用场景；
  • 可摘录的范围有限：浏览器内置 PDF、Canvas、视频画面、输入框、关闭的 Shadow DOM 和跨域 iframe 不可直接摘录。
这指向了下一阶段最核心的问题：

如果“摘录中转站”只在浏览器里存在，那么它解决的就只是网页内的复制，而不是用户在电脑上的全场景复制工作流。

2 用户调研与问题验证

为了确认问题是否真的普遍存在，同时补充场景和指导产品取舍，我围绕以下问题访谈了 5 位用户：

  • 你在什么情况下需要复制内容
  • 复制时最麻烦的步骤是什么
  • 完成多段内容复制任务时的流程

2.1 访谈中最明确的四类痛点

痛点 用户的实际困难 为什么现有复制方式不够好
长段落首尾难定位 使用触控板时要一直按住，跨屏拖动容易窜位；回调起点、终点也很难 系统选择手势要求用户持续控制整段路径，而用户真正只关心两个端点
同一页面内选取多处 想保留一篇内容中的几段，只能复制、粘贴、返回，多次重复 剪贴板一次只保存当前项，没有“暂存多个候选片段”的空间
跨界面组合内容 需要从网页、聊天、文档或多个页面取材时，必须频繁切换窗口 复制动作把信息收集与最终整理强制绑在一起
想保存当前内容才能继续复制 一旦复制了下一项，上一项就会被覆盖，因此必须先找地方粘贴 用户被迫过早决定保存位置和最终结构，打断当前任务

2.2 可类推的真实场景

以下场景是基于访谈问题和实际工作流程做出的产品推演：

用户／场景 需要摘取什么 中转站的作用
Agent 使用者 从需求、日志、文档和对话中拼出完整上下文 先收集事实，再按 Prompt 顺序组合

2.3 用户问题的本质

通过访谈我意识到，用户面对的并不是单一的复制困难场景，而是一条「复制粘贴」工作流中存在的四个断点：

  1. 如何更容易地确定范围；
  2. 如何让多个复制项同时存在；
  3. 怎么在复制前调整取舍和顺序；
  4. 如何把结果一次性送到真正要使用的地方。

因此，产品不能只做选中文字方式上的升级，也不能只做一个无限保存历史的剪贴板。

它必须同时提供“定位、暂存、编排、输出”四个环节。

3 竞品分析：市场不缺大而全的工作区，缺的是轻量摘录的中转站

3.1 竞品选型与调研

本项目的竞品调研是基于用户从“看到内容”到“组合并使用内容”的完整过程，而非限于相关产品。

类型 擅长什么 与本需求的差异 对本产品的启发
系统原生复制／剪贴板 学习成本最低，任何软件都能使用 一次通常只承载一项；不负责多片段编排 保留原有复制心智，不创造复杂工作流
剪贴板历史工具 保存文本、图片、文件等历史，支持搜索、收藏 功能全面但信息量大；主要围绕“找回过去复制过什么”，不是“围绕当前任务组装几段内容” 不做无限历史，把当前任务所需内容放在最前面
笔记／知识库工具 长期保存、分类、链接和检索 用户必须立即切换过去、选择位置并粘贴；记录结构较重 中转站只负责临时收集，不替代长期笔记库
现有中转站类工具
（多为个人 vibe coding 作品）		 文本、文件、图片、链接等多形态内容的暂存 可暂存的种类很多、也通常带有派生功能如番茄钟等 做轻量文本中转站，而非兼容全部格式、形态的工作区

3.2 现有中转站类产品为什么容易显得“大”

许多相关产品同时承担剪贴板历史、图片暂存、文件管理、搜索、收藏、标签、同步甚至自动化。功能越完整，产品越接近一个长期资料库，界面也需要展示更多类型、时间、来源和管理入口。

这些能力虽然本身有价值，但会带来两个与本项目目标相反的结果：

  • 用户要先理解一个新的内容管理系统；
  • 临时摘取几段文字时，也要面对全局资料管理的复杂度。

“摘录中转站”选择了一个更“窄”的位置：不保存全部复制历史，不承担长期资料管理，只服务“当前这次文本摘录任务”。

3.3 市场空位

本产品不追求兼容的类型的种数，而追求用户在阅读过程中的无感复制体验。

由此形成的产品空位是：

在系统剪贴板、全能工作暂存区和长期笔记工具之间，提供一个能够精准定位、多项共存、按序组合、用完即清的轻量摘录工作区。

4 产品定位与用户画像的最终确立

产品定位

一个用两次定位代替长距离拖选，让多处内容先暂存、再按顺序一次性复制的桌面轻量摘录中转站。

4.1 解决的问题和核心价值

当我在阅读网页、Agent 对话、文档或业务资料时，如果需要摘取多个不连续位置的内容，我希望不用反复切换到目标应用，而是先连续收集、调整顺序，再一次复制，从而保持阅读和思考的连续性。

价值 产品如何实现
更容易选准 用户只指定首字和尾字，不必拖过中间全部内容
不打断当前任务 悬浮按钮常驻，片段先进入中转站，用户继续阅读
多项可以共存 每个片段独立保存、选择和删除，不被下一次复制覆盖
结果可重新组织 六点拖拽改变顺序，组合复制遵循看板顺序
用完即清 片段只属于当前会话，退出或主动清空后不形成长期负担

4.2 核心用户画像

  • 经常在长内容中选择多个非连续段落的人；
  • 习惯使用触控板、对长距离拖选控制困难的人；
  • 需要把网页、文档、聊天或多个软件中的信息组合起来的人；
  • 希望保持阅读流，不愿每次摘录都切换笔记工具的人；
  • HR、客服、答疑、运营、研究、写作和 Agent 重度使用者。

4.3 明确不做什么

  • 不做无限期保存所有复制记录的剪贴板历史库；
  • 不做完整笔记、知识图谱或文件管理系统；
  • 不做文件、图片、链接等多形态内容的暂存；
  • 不要求用户学习标签、分类和自动化规则。

产品边界越清楚，悬浮中转站才越可能保持轻量。

5 产品演进与关键决策：从浏览器到 macOS

5.1 MVP版本

已有的浏览器 Demo 版本，经 10+ 项功能补足和 ui 调试之后，形成本产品的MVP。浏览器最终版支持 Chrome 116+ 与 Edge，采用 Manifest V3。核心能力包括：

  • 精确到字素的两次点击定位，包含首尾两个字符，避免截断 Emoji 和组合字符；
  • 起点确定后可跨多屏滚动，也支持先点末尾、再点开头；
  • 定位第二端时，动态显示起点到当前字符之间的文字衬色；只有第二次点击才真正生成片段；
  • 支持标准网页 DOM 中的标题、段落、粗体、链接、列表、表格、代码块和标准图片；
  • 多片段暂存、勾选、全选、逐条删除、批量删除、撤销删除和六点拖拽排序；
  • 新片段自动复制，组合复制严格遵循看板当前顺序；
  • 双按钮／单按钮两种最小化形态，均可整体拖动；
  • 四种颜色设置：蓝色、黄色、红色、绿色，默认蓝色；
  • 片段上限 50 段、合计约 8 MB；内容只保留在当前页面内存中。

下一阶段的开发目标是为解决“频繁切换页面”这一痛点，而开发macOS全局版应用。

5.2 产品决策一：从范围衬色改为首尾定点

浏览器版基于 DOM Range，可以较自然地拿到每一行文字的矩形，因此最终保留了“起点到当前字符之间的文字衬色”作为动态预览。

到了 macOS 全局版，产品最初也尝试复刻这套体验，但连续遇到三个问题：

  1. 有些应用只能返回一整行或一个大矩形，无法精确展示从哪个字到哪个字；
  2. 跨段落时，辅助功能树可能把内容拆成多个不同节点，难以得到连续、稳定的每行几何范围；
  3. 鼠标移动过程中不断查询多段文字矩形会产生明显卡顿，选中衬色只能在同一行生效，无法丝滑覆盖长内容。

若继续追求“像系统拖选一样给全部文字上色”，会让产品投入大量适配成本，同时仍无法保证能够在所有应用中稳定成立。因此最终做出整体调整：

  • 不再展示中间范围衬色；
  • 第一次点击锁定首字或尾字，并给该字符加底色；
  • 第二次点击锁定另一端字符，同样加底色；
  • 系统只需准确表达“这两个字是范围端点”，中间内容由文字结构计算，不再要求绘制完整选区。

最早的端点只用竖直光标表示，视觉不够明显。最终提供三种可选定位标记：

  • 小旗；
  • 地图定位点；
  • 准星。

标记与系统原光标同时显示，尺寸足够清楚；选中的首尾字符底色、定位标记和悬浮按钮统一使用用户自定义选择的颜色。

这个决策不是降低效果的无奈之举，而是通过剖析用户行为本意（选中首尾）产生的替代方案，并重新明确产品承诺：不能为了保留形态而牺牲产品的使用流畅度和稳定性。

5.3 产品决策二：增加输入框，而不是假装全局识别无边界

macOS 辅助功能接口能否返回文字，取决于目标应用是否具有公开可访问结构。我调研了Canvas、视频、图片、部分 PDF／Office 页面和一些复杂编辑器，发现这些应用并没有直接的可供读取的文字范围。如果想要兼容全部应用，必然耗费大量的精细调研及开发成本，也不是短期内能达成的目标。而如果产品只提供全局取词，一旦识别失败，用户的整个工作流就会中断。

为此，我为展开面板增加了手动输入框：

  • 用户可以直接输入自定义文字；
  • 也可以把其他方式（如手动粘贴）获得的内容粘贴进来；
  • 粘贴后不会立即生成片段，内容完整保留在输入框中；
  • 普通回车才确认并加入片段，Shift + 回车换行。

这个输入框不只是技术兜底，也扩大了产品的可玩性：用户可以在摘录片段之间加入标题、解释、过渡句或自己的判断，主动组织出一段更完整的最终复制内容。

因此，产品从“只能摘取现有内容”扩展为：

摘取外部内容＋补充自定义内容＋按意图重新编排。

5.4 产品决策三：新片段加入时的头插 or 尾插

对于“新片段加入时，应位于片段列表顶端还是尾端”这一问题，Demo 中最初的设定是默认尾插，即新加入的片段会出现在片段列表的末尾。
在加入“输入框”相关功能后，为了使用户在回车后对“成功加入片段”有明确感知、新加入的内容会直接出现在列表最顶端，我将新片段加入的方式改为了头插 -- 片段列表倒序、新加入的内容置顶。

但实际使用时却暴露了更严重的问题：中转站不只是确认列表，它还决定最终组合复制的顺序。例如，用户按照文章顺序依次摘取“背景—问题—结论”，倒序会自然变成“结论—问题—背景”，这与产品的组合功能相冲突。

最终调整为：

  • 新片段按录入时间正序追加到列表末尾；
  • 第一条“片段1”在最上方，最后加入的片段在最后；
  • 自动反馈由整个“+”按钮轻微闪动承担，同时在输入框中写明提示“回车即可新增片段”，不再依赖置顶确认；
  • 用户仍可通过六点按钮拖拽改变最终组合顺序；
  • “复制所选”严格按照看板从上到下拼接。
这次取舍的思考与反思：

产品功能不能在逻辑上相悖；新增一个功能或改动时要先从用户视角体验路径，全局思考判断。

主动拒绝 密码框、受保护／安全输入内容 出于安全原因不读取

6.3 浏览器版与 macOS 版的关系

两者不是互相替代，而是同一产品在不同环境中的能力实现，亦可满足不同使用需求和使用场景的用户自行选用。

对比项 Chrome／Edge 扩展 macOS 应用
覆盖范围 当前网页标签页 多个桌面应用中的可访问文字
文字来源 DOM Range AXRange、AXTextMarker、飞书专用适配
中间衬色 支持动态文字范围衬色 只显示首尾字符和定位标记
网页富文本 更可靠，可保留 HTML、列表、表格、代码和标准图片引用 取决于目标 AX 数据，常降级为基础富文本或纯文本
不可读内容兜底 无手动输入框 支持输入／粘贴后回车建片段
跨应用 不支持 多个片段可以分别来自不同应用
数据生命周期 当前页面内存 当前应用运行会话内存
共同能力 两次定位、多片段、选择、删除、排序、组合复制、自动复制、双／单悬浮形态 同左

6.4 隐私、权限与发布边界

  • 浏览器扩展只在用户主动点击后访问当前标签页，不读取剪贴板、不上传内容、不发送分析请求；只在本地保存颜色和悬浮形态偏好。
  • macOS 应用本地运行，不包含云同步和内容上传；日志只记录不含正文的失败类型、界面角色、进程和耗时。
  • macOS 全局取词必须获得“系统设置 → 隐私与安全性 → 辅助功能”权限。
  • 权限绑定具体应用身份和副本；升级、签名变化或存在多个同名副本时，可能需要移除旧权限条目并重新添加当前应用。
  • 当前本机包采用本地验证签名。正式公开分发前仍需稳定 Developer ID、Hardened Runtime、安全时间戳、Apple 公证与票据装订。

7 产品原则与展望

7.1 产品原则

  1. 先保持用户的阅读节奏，再追求功能完整。
  2. 用户只给首尾，系统处理过程。
  3. 多个内容先共存，最终结构稍后决定。
  4. 中转站服务当前任务，不制造新的长期整理负担。
  5. 默认顺序必须符合最终输出语义。
  6. 成功反馈要可感知，但不能抢夺注意力。
  7. 界面只展示完成当前任务真正需要的信息。
  8. 无法稳定实现的效果不伪装成通用能力。
  9. 遇到技术边界时提供可理解的兜底，而不是让任务中断。
  10. 浏览器和桌面层各做自己最擅长的事，不用一个入口勉强覆盖所有内容。

7.2 下一阶段关注的指标与开发计划

方向 要回答的问题 指标／方法
摘录效率 两次定位是否真的比拖选更快、更准 长段落任务完成时间、首尾修正次数、失败率
阅读连续性 用户是否减少了应用切换 单次任务切换次数、连续摘录段数、主观打断评分
多片段价值 用户是否真的组合多段，而不只是复制一段 每次会话片段数、组合复制比例、拖拽排序比例
兜底能力 输入框是否弥补不可访问界面 手动输入／粘贴占比、失败后成功完成率
支持矩阵 哪些应用最值得优先适配 按目标应用统计成功率、纯文本降级率、Badcase
长期价值 产品是否从演示功能变成真实习惯 周留存、重复场景、用户回访与卸载原因

Windows 版将在 macOS 的产品交互和数据模型稳定后，复用产品规范继续开发。

思考

💭

什么才是用户真正需要完成的操作，什么是产品应该解决的问题。

  • 最初，我想用“首尾定位”解决长文段难以拖选，再用“多片段暂存”解决后一次复制覆盖前一次的问题；
  • 但用户调研让我看到，拖选困难只是入口，真正被打断的是从阅读、收集到整理和使用的完整过程：用户被迫反复切换窗口，并在信息尚未收集完整时，提前决定粘贴位置和最终结构；
  • 竞品分析进一步证明，市场并不缺功能完整的剪贴板、工作区和资料库，真正稀缺的是一个只服务当前任务、不要求用户长期维护的轻量中转站；
  • 从“全程衬色”改为“首尾定点”、从新增置顶改回按序尾插，再用输入框承接不可读界面，也让我进一步意识到：产品不能执着于复刻某种交互形式，也不能孤立地优化单点反馈；所有取舍都应服从最终输出语义和任务能否稳定完成。
💡

这也是我在整个项目中的思考：

一个好的效率工具，不在于覆盖所有可能，而在于顺应用户习惯、安排行为发生的时机：让用户只在必要时做必要的决定，让产品接住重复操作与技术复杂性，并用清晰的边界保证核心任务不被中断。
